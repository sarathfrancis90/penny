# P5b Android automatic backup — local evidence

2026-09-13, API 36 Android 16 arm64 emulator, isolated `ca.penny.offline.dev.test`. This extends the accepted manual P5 slice with an optional WorkManager path. No real Google account consent, token exchange or private Drive upload was performed. P5b exceeded its soft 10k implementation budget to close two independently reviewed persistence/consistency defects; no unrelated platform/polish scope was added.

## Behavior and guards

- WorkManager **2.11.2** stable, one unique periodic request `penny-private-drive-backup`, default off. A 24-hour interval/6-hour flex and initial 15-minute delay express eligibility, never a delivery-time promise. Network connected and battery-not-low constraints apply. ACCESS_NETWORK_STATE is now declared for those constraints; exact-host TLS policy remains unchanged.
- Explicit enable requires the configured signed app, previously enabled account/vault binding and confirmed recovery key. Desired schedule UUID and automatic state are encrypted with the existing cloud settings. Reopen reconciles persisted intent with unique WorkManager state. Work input contains only schedule identity, no token/key/account/financial data.
- A run checks pending data before authorization. Unchanged data and stale schedule IDs create no objects and do not authorize. Silent AuthorizationClient calls never launch a resolution/account picker. Missing consent, identity/key/vault/configuration mismatch, quota, capacity or verification failure requires foreground attention; transient connection/server errors have at most three attempts, exponential 30-minute backoff and an eight-minute coroutine deadline. HTTP connect/read timeouts still bound any blocking network tail. Token cache cleanup includes late SDK completion after cancellation.
- A single process-wide lease, epoch, job cancellation and lock coordinate foreground actions, worker activity, protected settings/key reads and writes, and local restore. No lock spans network IO. Foreground actions preempt background work. Late callbacks cannot commit or overwrite current session UI. Protected settings and recovery files are serialized across instances. Core database writes continue independently of provider latency.
- Before publication, snapshot data, data revision and vault incarnation are captured in **one SQLite transaction**, including when foreground and worker use separate VaultStore instances. The durable publication revision remains unique per attempt, while last-good data revision accurately describes the backed-up records.
- Automatic stop has an independent durable marker. Opt-out, retry/attention handling and protected-read failure write it before attempting fallible settings work. A verified retry-state write can clear it; failed persistence leaves it until explicit successful re-enable. Reopen checks it before scheduling or authorizing. A failed retry-state write propagates and never returns RETRY. Failed settings reads cancel work, clear automatic UI state and reset reconciliation. Manual backups and prior remote objects remain intact.
- Restore changes the durable vault incarnation and cancels scheduling/session state. Pending cloud preview still rechecks the selected account, key, epoch and local revision before replacement. No retention deletion, cross-writer winner or remote synchronization was introduced.

- `p5b-process-run.log`, `process-create.log`, `process-restart.log`, `process-verify.log`: external force-stop and fresh-process verification pass; PID **22761 → 22810**. The process test removes only its own expense.
- Native iOS cloud pair import is mandatory in CloudDeviceTest via shared `native-exports/ios-cloud-v1.{pennymanifest,pennybackup}`. Android authenticates the descriptor, fully decodes receipts and compares all eight snapshot arrays. These are public synthetic fixtures, not user backups.

The initial passing runner tests did not establish persistence failure or two-connection snapshot consistency. Independent review found both gaps. New device regressions inject failure after settings write and verify the stop survives reopen, and interleave a second database writer at the former snapshot/revision gap. The worker checkpoint blocks that write until its own snapshot/revision transaction is complete. Both corrections passed; failed behaviors were not suppressed.
