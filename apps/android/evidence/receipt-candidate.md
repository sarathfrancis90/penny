# Inactive receipt preparation

`VaultGenerations.beginReceiptPreparation` accepts receipt-free typed metadata and complete receipt declarations at existing limits. It freezes the metadata lists, validates model/reference rules and exact schema-3 serialized capacity using calculated base64 lengths, and requires existing settled authenticated state and an existing device key. It does not initialize, recover, change, or activate the current vault.

Single-use preparation accepts one bounded byte array or owned `InputStream` at a time. Stream input requires declared length, true EOF, successful close and cancellation checks; temporary bytes are wiped. Every receipt is sealed and fully native-decoded. Finish requires complete coverage, authenticated inactive rows/membership/receipt verification and successful verification-handle closes. It returns only an opaque candidate with immutable summary. Original file/directory ownership pins remain private until discard, so identical ciphertext copied into a different inode does not become owned.

Per-database candidate pins protect receiving and finished generations from normal GC across store connections. Successful discard removes only owned inactive rows/files and wipes the retained key. Cleanup uncertainty retains ciphertext/catalog/key conservatively. Candidate receipt catalogs use private **format 2**, meaning unexposed, non-resumable intent; active/legacy catalogs remain format 1. The existing collector refuses format 2, including after restart. Such intent is never automatically promoted, installed or made eligible for deletion through authenticated reopen. Future guarded installation and abandoned-intent handling require a separate reviewed handoff.

Existing Snapshot preparation/replacement is unchanged. This is an internal reusable preparation seam, with no public installation capability, UI/Drive/v4 integration, cap increase, constant-memory or performance claim. Metadata arrays remain temporarily materialized. Callers must close owned preparation/candidate handles.

Final build, 25 JVM tests and lint passed. API 26 and API 37 each passed **32/32** focused tests: candidate 7, metadata 4, generation 5, receipt 8, mutation 4, local cancellation 2 and raw migration 2. [Exact hashes, commands and shared-scenario mapping](receipt-candidate.json) distinguish executed preparation cases from the three unimplemented installation cases. Tests verify frozen inputs, exact all-domain/receipt roundtrip through a test-only authenticated inactive reopen, unchanged current state/key, invalid/missing/duplicate/native-invalid receipts, input length/read/close/cancellation, one-shot transfer, shared-connection GC protection, and same-ciphertext inode/foreign-entry preservation after discard and reopened-store GC.

The write/close scenario is explicitly partial: builder injections occur after real verification closes or carry simulated cleanup uncertainty; existing foundation tests separately cover write/sync/close checkpoints and partial writes. No real FD-close failure, disk-full or fresh-process candidate recovery proof is claimed. A prior 31/32 run is retained: the test initially expected successful cleanup where the ownership guard correctly returned `ENOTEMPTY`; corrected assertions require preservation and later GC quarantine.
