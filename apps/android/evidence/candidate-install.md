# Guarded local candidate installation

This slice connects the internal raw-receipt preparation capability to `VaultStore.installPrepared`. It does not add UI, cloud/provider, v4, larger caps, or resumable candidate APIs. The existing Snapshot replacement facade and missing-key recovery policy remain unchanged. New preparation requires an established authenticated local vault and an existing device key.

`beginReceiptPreparation` freezes metadata and binds the receiving store's authenticated active state, source contents, revision/incarnation, restore binding and wrapped-key identity. Retained nofollow descriptors pin the actual SQLite main-file inode, noBackup directory and existing receipt-root directory; a newly created receipt root is pinned before input. Checks bracket source capture and run again at installation. Receipt-free candidates have the same database/noBackup guards. The same open SQLiteDatabase connection is required: a closed/reopened connection is stale. Candidate operations lock by captured DB path and check namespace identity before any lazy database reopen. Android stores cloud writer identity separately; this local API adds no cloud writer/account linkage.

Only the receiving instance can install its candidate. A foreign receiver cannot consume the legitimate owner's handle; the first owned installation attempt consumes it. The shared existing publication helper verifies candidate data and retained receipt ownership pins, authenticates its format2 catalog, and adopts format1 inside the same transaction as the active pointer. The predecessor stays complete until authenticated new reopen resolves the pending journal. Cancellation wins before the publication CAS; afterward commit/recovery owns the outcome. An error after CAS releases ownership pins without deleting possibly published files/key/catalog. A rolled-back format2 catalog remains quarantined. Cleanup on namespace loss does not write to the replacement database.

Final validation passed 38/38 device tests on API37 and API26, 25/25 JVM tests, build and lint. The focused device set includes the six new installation groups and existing candidate preparation, metadata, receipt foundation, durable generation/recovery, expense rollback, local cancellation and raw migration tests. Exact commands, source/APK/report hashes and scenario mapping are in `candidate-install.json`; frozen files are under `artifacts/offline/candidate-install/final/`. Earlier 37-test pre-namespace runs remain historical.

The three previously pending shared installation scenarios now pass: all eight domain arrays/IDs/time and original receipt bytes reopen exactly, an intervening edit survives stale install rejection while a candidate stays GC-pinned, and a repeated numeric revision under a new authenticated incarnation rejects. Extra cases prove source-digest-only mismatch, current key loss/envelope corruption, row/receipt/inventory tamper, pre-CAS/late cancellation, actual SQLite transaction abort, committed interruption and invalid-pending predecessor rollback. Namespace tests copy identical database bytes, copy the whole noBackup directory, replace just the receipt root, or close the receiving connection; rejection preserves the new namespace. Database/whole-root/closed cases use receipt-free candidates.

Reopen evidence uses new store instances in one process. It does not establish process-kill, real power-loss, full-volume or OS close-failure behavior. Existing preparation close/write annotations remain partial injection where applicable. Metadata arrays and full existing native image checks remain; no memory, speed or expanded-capacity claim. Test sandboxes were force-stopped; normal demo data/APK were unchanged and API26 remains available for integration coordination.

A final review probe also passed 1/1 on each API after the 38-test suite: copying the main database to its existing pathname **before** candidate begin while retaining SQLite’s old open connection causes actual `SQLiteReadOnlyDatabaseException` code 1032 (`SQLITE_READONLY_DBMOVED` on API37). Preparation rejects and copied pathname bytes stay unchanged. This adds only one test method; the prior tested source is frozen beside the follow-up APK/logs under `before-begin/`. Production source and app APK are unchanged.
