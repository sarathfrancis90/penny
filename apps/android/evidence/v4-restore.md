# Internal v4 candidate restore

`VaultStore.prepareV4` now validates encrypted v4 input into the existing owned receipt candidate. `restoreV4` prepares and installs through the existing guarded publication/recovery protocol. Neither API is wired to UI or providers; existing v1–v3 backup selection, caps and missing-key recovery policies remain unchanged.

An opaque receiving-target capability captures authenticated local state, source digest, revision/incarnation, key envelope and pinned namespaces before input acquisition. After pass1, candidate preparation atomically revalidates that original capability; it cannot acquire newer authority. Pass2 target changes remain subject to the original installation guard. A valid candidate may have become stale during pass2, but its installation rejects and preserves the intervening edit.

The input is acquired once into an exclusive private ciphertext file, bounded to20MiB during copy. The writer is synced/closed, permissions become read-only, and original file/root descriptors remain pinned. Each decode pass reopens the owned snapshot, checks identity, counts/hashes every byte through actual EOF, and requires its SHA256/length to match acquisition. Both complete logical summaries/transcripts must match. Input/sink closes and post-close cancellation checks precede candidate success; owned ciphertext removal, directory sync and descriptor closes also precede preparation finish. Cleanup preserves substituted names at the tested boundaries; it is not a universal race-proof guarantee against a concurrent same-UID filesystem adversary.

Pass1 retains bounded receipt-free metadata/declarations and discards native-validated receipt bytes. Pass2 forwards each authenticated, native-validated borrowed receipt directly to existing encrypted preparation. No decoded plaintext files or aggregate receipt base64 are created. Existing exact schema3 exportability sizing remains the candidate gate. The recovery root is a separate caller-supplied32-byte key, copied only after validation and wiped best-effort; device-key creation is forbidden in this path.

Final focused tests passed25/25 on API26 and API37; JVM25/25, build and lint passed. Seven new restore groups ran alongside four app-reader, seven preparation and seven installation groups. The new path installed two exact shared encrypted layouts and test-framed finance/split fixtures, then reopened durable data. The finance case compared all eight domain arrays to snapshot-v3, and image bytes were compared exactly. A preparation hook prohibited aggregate Snapshot hydration.

Negative tests cover truncated/tampered/missing-final/trailing/wrong-key input, malformed authenticated logical records, current-cap rejection, a CRC-valid native-invalid PNG with recomputed descriptor/transcript, source read/close faults, cancellation, target edits during both passes, key loss, and ciphertext replacement/mutation/truncation/append before pass2. Existing candidate tests re-established exact capacity, foreign-owner/single-use, namespace, late cancellation, SQLite abort and pending rollback behavior. Fault callbacks at sink/source close are explicitly checkpoint injections; no actual OS close/full-volume/power-loss proof is claimed. Reopens use new store instances in one process. No new opposite-native writer export was generated.

`v4-restore.json` pins source/APK/logs, exact commands and all ten shared acceptance IDs, with scoped limitations. Raw output is under `artifacts/offline/v4-restore/`. Cancellation is cooperative at bounded I/O and sink boundaries; an arbitrary blocking provider stream may delay it. Normal demo data/APK remain unchanged, sandbox processes were stopped, and API26 remains available for coordination.
