# Android capacity v4 assessment — proposal only

Assessed 2026-09-13 against the current native Android source. This document changes no runtime, local schema, portable format, capacity limit or release status. Existing v1–v3 readers, minimum API 26, current API 37/16 KiB runtime checks, no-account local operation, optional on-device AI, and validation before commit remain requirements. Earlier P6 performance numbers below are recorded measurements, not new benchmarks.

## Recommended direction

Keep encrypted SQLite rows and the Keystore-wrapped random data encryption key (DEK). Remove full-vault work from ordinary mutations; detach receipt ciphertext into immutable private files; introduce a separately versioned streaming backup and candidate restore. Do not raise `Snapshot` or `Backup` constants in place. Coordinate the exact wire bytes, limits and adversarial vectors with the contract and iOS designs before implementation.

The planning workload is 50,000 expenses plus a multi-year receipt collection. The contract proposal currently considers 50,000 receipts, 2 MiB per image, 8 GiB aggregate receipt bytes, 256 MiB metadata and 9 GiB maximum wire bytes. These are independent provisional ceilings, not all simultaneously saturable, and are not release promises. At 50,000 receipts, 8 GiB permits about 168 KiB per receipt on average. Current maximum-length text can exhaust metadata capacity before 50,000 records. Capacity UI must report remaining bytes as well as counts, and every accepted save must remain exportable.

`docs/offline/PERFORMANCE.md` records a final API 37 emulator sample: 10k reopen 1.108 s; edit 1.160 s plus refresh 1.066 s; export 239 ms; decode 1.068 s; replacement 1.397 s. PSS 303,530 KiB was an operation-boundary sample in the UI/OCR process, not peak memory. Multiplying these by five is not evidence for a 50k workload.

## Incremental validation, reads and reports

First implement a serialized repository view tagged with database revision, incarnation and authenticated key-generation identity. Build its metadata maps from authenticated rows, without loading receipt contents. Unwrap/check the current key before each operation; a process cache must never make a deleted/replaced Keystore key look usable. Invalidate on another connection's revision change or restore. Do not replace the current safety check with Android key-object equality.

Maintain ID maps, receipt-owner maps, recurrence/source-occurrence sets, exact encoded metadata byte counters, checked aggregate cents, month/category totals and savings/source lookup maps. A mutation validates the changed row, its references, uniqueness and impacted aggregate invariants against that validated view, then atomically writes affected rows, encrypted derived state and revision. Serialize these checks with the write transaction, including the second-connection case. Publish a UI delta only after commit. Cache invalidation after a failed commit is mandatory. Full import/open/export validation remains an independent integrity path and comparison oracle; no invalid record can hide behind cached totals.

Keep search/report indexes in memory initially. Never put merchant, dates, category, amounts, notes or search tokens into plaintext SQLite/FTS. If cold-open memory requires persistence later, encrypted index pages need their own authenticated revision binding and rebuild path. A 50k decrypted model cache must be measured, not assumed affordable. A later encrypted page store or SQLCipher adoption is a separate migration/security/dependency decision, unnecessary for this first improvement.

Move search, month aggregates, rollover and due computation off composition into revision-keyed repository queries. Preserve the exact case-insensitive search semantics and money/rollover goldens. One pass creates month/category sums and source maps; process the historical budget chain over those sums. Invalidate rollover from the edited month onward. Use occurrence sets for idempotency and due display. Publish only requested pages/rows to Compose, keep stable IDs and derive receipt counts from metadata. Decode one receipt on IO with cancellation; bound any bitmap cache by bytes. Stream formula-safe CSV rows to the chosen output, preserving ordering and Unicode behavior.

## Detached receipts and durable generations

Introduce local-only `ReceiptDescriptor`/`ReceiptBlobStore` instead of reusing legacy `Attachment.dataBase64`. Keep descriptors encrypted in SQLite and image bytes encrypted in immutable files under `noBackupFilesDir`. Names are locally generated random IDs resolved under one fixed root, never archive paths or plaintext content digests. Bind each local blob cryptographically to its format, vault/generation, random file identity, attachment ID, owner, length and digest. Use domain-separated keys/AAD and fresh nonces; do not copy archive nonce construction into another key domain casually.

One receipt is still bounded to 2 MiB, so sequential full receipt authentication and native image decoding can remain bounded even though the collection is large. At most one 16-million-pixel decode should be live during validation; such a bitmap alone can consume roughly 64 MB. Retain current API 26 PNG/JPEG strictness and API 28 HEIC preparation boundary. Thumbnails stay encrypted or memory-only; no plaintext temporary JPEGs.

For an ordinary add: validate image/descriptor, create exclusive encrypted temporary file, flush/sync, reopen/authenticate, rename to immutable final name and sync its directory; only then insert descriptor/expense and bump revision in SQLite. A failure before SQL commit leaves an unreferenced encrypted orphan, not an expense pointing to incomplete bytes. Delete commits reference removal first; defer file reclamation until no active generation, export lease or rollback candidate references it. Missing saved blobs fail closed, never silently disappear from a backup.

For migration and restore, use generation-scoped rows in the same SQLite database plus an active-generation pointer. Build a candidate generation incrementally with its own wrapped DEK; write and authenticate all referenced files before allowing preview. Final commitment is a short SQLite transaction that rechecks preview revision, incarnation, key binding, cancellation and cloud account/session guards, switches active generation and key envelope together, and bumps revision/incarnation. Keep the prior complete generation until new-state verification and durable commit succeed. All connections must resolve the active generation in their transaction; stale caches cannot continue writing it.

This is a proposed local schema migration, separate from portable schema 4. Migrate legacy inline receipts one at a time, preserving raw bytes and metadata, and validate all domains and totals before pointer switch. Keep the source generation intact until verification. Never replace the active wrapping-key alias while only preparing a candidate: a failed restore with a missing old key must not reset the old vault. Existing direct-Keystore-to-wrapped-DEK migration tests remain applicable.

Snapshot creation needs a coherent metadata/row copy and an immutable blob lease. Copy bounded encrypted rows into a private staging database under a short read transaction, capturing revision/incarnation; pin referenced files. Do not hold a live SQLite transaction through archive encryption, upload or readback. Never copy a live database/WAL or an independently changing receipt directory. Export from the pinned view, and release its files only when the operation closes.

## Streamed archive and Drive path

Add a v4 file/stream API alongside frozen legacy `Backup.decryptVersioned`; sniff only a tightly bounded prefix and reject unknown versions. The contract draft uses a fresh archive DEK wrapped under the recovery key, authenticated fixed header, bounded 1 MiB authenticated frames, individual finance/expense records and receipt descriptors followed by raw bytes. Frame sequence/length/finality and the terminal record counts/digest plus strict EOF must authenticate. Exact nonce/AAD/encoding belongs to the shared specification and golden vectors. Resume transmission of an already sealed immutable file; never reseal changed plaintext with an existing archive key/sequence.

Proposed APIs: `PreparedArchive(file, byteCount: Long, sha256, snapshotIdentity, revision, lease)`; `prepareArchive(checkpoint, key)`; `readArchive(input, boundedCandidateSink): ValidatedRestore`; `commitRestore(candidateToken, expectedRevision)`. The token references private encrypted candidate rows/files and authenticated summary, not a giant `Snapshot`. Parse bounded records with strict duplicate-key/UTF-8/integer rules, insert candidate rows incrementally and check cross-record identity/reference constraints before preview. Do not expose unauthenticated frame plaintext; keep decrypted frame buffers bounded and clear them after use.

Adapt `BackupExporter.exportVerified` to stream sealed staging to a new empty SAF destination and then stream destination readback through byte comparison/hash/authentication. Keep existing file preservation and failure semantics. Preflight free space for the active vault, candidate, encrypted archive, SQLite journal and reserve; actual write/fsync failures still preserve old state. Downloads may feed a bounded authenticated candidate sink while retaining only encrypted on-disk state. Document each mode's worst-case space instead of claiming streaming removes disk needs.

Add file-oriented transport methods with `Long` limits/offsets; keep small metadata/manifest byte arrays explicitly bounded. `DriveTransport.response` should retain its small JSON helper and add separate file upload and bounded download paths. Use `setFixedLengthStreamingMode(long)` with a fixed transfer buffer; this overload is available from API 19. [Android HTTP API](https://developer.android.com/reference/java/net/HttpURLConnection#setFixedLengthStreamingMode(long))

Use checked lengths for both declared and observed bytes, streaming SHA-256 and complete authenticated readback. A new cloud manifest version must bind the v4 envelope/schema and `Long` length, digest, identity and all provider segments if segmentation is selected. Keep the v1 manifest reader unchanged. If using bounded immutable provider segments for cross-platform parity, the manifest must authenticate ordered segment IDs/lengths/hashes and total length; capacity inventory reserves every new segment plus manifest. Missing/duplicate/reordered segments fail restore. The current two-object inventory allowance is insufficient for that mode.

Drive resumable chunks are transport boundaries, independent of archive crypto frames. Nonfinal upload chunks must be multiples of 256 KiB; use the acknowledged range rather than assuming all sent bytes arrived. Handle 308 only as the expected resumable-session status, still refusing redirects and unsafe session origins. Persist resumable session state only encrypted and bound to account/key/vault/publication revision/archive digest; never store tokens there. [Drive resumable upload](https://developers.google.com/workspace/drive/api/guides/manage-uploads)

Check active guards at bounded IO intervals, before/after network effects and before last-good. Cancellation must close/disconnect active IO, clean owned staging and leave prior last-good intact. Preserve complete pagination, independent writer choice, immutable publication, account reauthorization and default-off backup. No retention deletion is part of capacity work.

Large archives exceed current deadlines on realistic links. Keep the eight/ten-minute guards until a separately specified resumable operation can stop/reacquire authorization safely across bounded work sessions. Ship local/manual v4 capacity first if necessary; show large automatic backup as unavailable/pending support, never as verified. A successful small fake-provider test cannot establish 8 GiB Drive or scheduler support.

## Bounded implementation slices and acceptance

1. **Contract first:** freeze v4 framing, independent limits, terminal completeness rules and cloud manifest version; shared Node/Swift/Kotlin positives and malformed corpus. Legacy readers and every native captured archive still pass unchanged.
2. **Incremental metadata at old capacity:** replace full-save/refresh scans and add indexed calculations with cross-connection invalidation. Compare every mutation sequence against full validation/report goldens, including money overflow and duplicate recurring posts. Do not raise limits yet.
3. **Detached local receipts:** add generation migration and immutable blob lifecycle under old limits; fault inject each write/sync/rename/SQL/pointer boundary and external process death. Exact receipts and all eight domains survive migration; source remains recoverable on failure.
4. **V4 file backup/restore:** bounded sealed staging, candidate preview/commit and legacy upcast. Cross-platform captured native exports; all-component corruption, wrong key, truncation, reordering, trailing bytes, unknown version, oversized counts/lengths, duplicate IDs/owners and disk-full cases preserve active state.
5. **Drive v4 then resumable scheduling:** file streams, manifest/segment bindings, new inventory accounting and guarded remote readback. Verify account switch, expiry, cancellation, quota, denied SAF readback, dropped connection, contradictory ranges and changed revision at each await. Real registered-account clean-device recovery remains required.
6. **Measured capacity enablement:** only after both platforms pass the same accepted workload and restore every represented value. Surface the minimum of count, metadata, receipt, wire and available-disk budgets.

Provisional physical-device gates: release build, at least five repetitions at 1k/10k/50k records and separate 100/10k/50k receipt-count plus 8 MiB/1 GiB/8 GiB byte workloads. Include genuine image content and maximum pixel dimensions; padded tiny PNGs alone are insufficient. Publish cold versus warm median/p95, exact hardware/runtime, at-rest bytes, true peak heap/PSS, UI frame stalls and thermal behavior. API 26 and API 37/16 KiB emulators remain mandatory regression lanes; physical-device evidence is additional.

Targets to negotiate before enabling capacity: 50k cold ready under 5 s; ordinary single-row save/search/month report p95 under 150 ms; no storage/crypto/image decode on the main thread and no task-induced main-thread stall over 50 ms; streaming backup overhead at most 32 MiB above the measured metadata baseline, plus at most one bounded image decode; cancellation detected within one second in CPU/file loops and active network connection closure on cancellation. Double receipt volume without proportional heap growth. Verify >2 GiB offsets and actual multi-gigabyte files, not only mocked `Long` counters. Record archive throughput and local IO separately from network throughput; impose no invented cloud completion-time guarantee.

This assessment ran no runtime tests because it changes only this proposal. None of the acceptance targets above is established by writing the document.
