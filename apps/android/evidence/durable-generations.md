# Durable generation integration — bounded local evidence

The app's existing `VaultStore` API now delegates to `VaultGenerations`. Local SQLite schema 4 stores generation-scoped authenticated rows and detached encrypted receipts. Portable v1–v3 snapshots and the existing capacity limits are unchanged. Local restore previews and Drive confirmation additionally bind installation to the captured local state digest; existing revision/account/session/recovery checks remain in place.

`LegacyVaultRows` retains the schema 1–3 migration reader. An authenticated first-migration journal binds the validated legacy content, source vault, revision and incarnation before preparation. Missing active markers cannot bootstrap an empty vault when established generation evidence exists. The journal and legacy tables are removed together only after authenticated activation. Each new generation has its own wrapped random key; preparation leaves its predecessor's envelope unchanged. Active state and its pending predecessor are authenticated independently under the device wrapping key. A pending invalid replacement can recover its recorded verified predecessor. Established corruption stays locked.

The private local format uses explicit version 1 and separate alias-bound AAD domains for active state, migration journal, generation keys, headers, rows and receipt-group catalogs. Headers retain snapshot/vault identity, timestamp and a digest over exact record membership and receipt descriptors. The active state carries revision/incarnation and a pending predecessor's prior revision/incarnation. Android's cloud writer ID remains in the existing separately protected `CloudSettings`; it is not moved or reset by ordinary store writes.

All store instances for the same database share a lease. SQL transactions and that lease protect coherent Snapshot hydration and installation. Receipt read leases release descriptors without deleting committed files. Unchanged receipts reuse their immutable file group; changes create and verify a new group before rows/reference changes commit. Cleanup removes fully authenticated, unreferenced groups and preserves ambiguous, partial or foreign entries. Quarantined physical staging space is not yet comprehensively bounded. No long-lived exporter file lease is exposed: the current exporters receive hydrated in-memory snapshots.

## Actual validation

The final local/cloud cancellation correction built with sandbox APK assembly, JVM tests and Android lint. It passed **3/3 focused device groups on both API 26 and API 37**: actual local-file ViewModel preview/replace/cancel before publication, late cancel after publication with truthful success, staged candidate tamper before publication, and the fake Drive guarded restore regression. One method exercises both local cancellation boundaries, duplicate Replace admission and an injected verification failure after publication. The fake Drive discover/select/preview confirmation also tests cancellation at FILES_READY retaining a local edit and late cancellation after POINTER_COMMITTED completing the source snapshot, alongside its existing account/key/revision/session/expiry guards. The typed cloud confirmation callback receives the same `RestoreOperation` from the ViewModel and passes it into storage; it cannot silently use a separate default token.

The runtime guard is checked during receipt writes, row writes and after preparation. An atomic transition immediately before the active-state write is the publication linearization point; Cancel wins before it, while later Cancel leaves the committing preview intact and cannot report that the old ledger was retained. Finally settles the operation and consumes the preview even after a failure, preventing an undismissable or nonfunctional retry dialog. Restore errors use neutral guidance to reopen and verify the vault; they do not assert that the old ledger was kept after publication.

Before that correction, both API 26 arm64/4 KiB and API 37 arm64/16 KiB passed **28/28 selected device groups**. These include seven receipt-foundation regressions, the shared all-domain generation inputs, schema 2/3 and direct-Keystore migration, maximum-size receipt migration, second-connection changes, transactional rollback, key loss/corruption, no ViewModel success before commit, finance posting and fake Drive guarded restore. The fresh-process test then passed two separately selected invocations on each device: a pending pointer was left after an injected checkpoint exception, the host force-stopped the sandbox, and a different PID authenticated the replacement on reopen. Those runs remain historical evidence for their recorded source/APK hashes; they were not rerun for the final bounded cancellation correction.

The runtime-discovered inode-reuse fix remains in place. Independent review additionally found and corrected the missing-both-markers empty-reset path and a descriptor leak if durable reopen failed during pin admission. The missing-marker regression executes on both devices; the pin cleanup fix has source review and the successful reopen regression, not an injected kernel `fstat` failure.

[durable-generations.json](durable-generations.json) records final source/APK/fixture/log hashes plus the historical 28-group/PID evidence and each shared lifecycle scenario's precise coverage. It explicitly distinguishes same-process checkpoint tests, reopened store instances and the actual different-process pending-valid case. Termination during a write, a long-lived exporter pin and a separate catalog-GC foreign-entry scenario do not have complete dedicated runtime coverage here. No physical power-loss, full-volume, signed-release or performance gate is claimed. The earlier foundation report remains the historical source checkpoint; its source hashes should not be attributed to this changed implementation.

## Hot-path cost and next focused gate

`all()`, `finance()`, `attachments()` and `vaultId()` currently hydrate a complete Snapshot. `revision()` remains a small metadata read. Durable reopen verifies each receipt before `read()` decrypts and decodes it again. A mutation reads the prior snapshot, compares decrypted existing rows, and fully reopens the resulting generation before commit. Only changed rows are encrypted/written, and ordinary edits reuse receipt files, but there is additional read/validation work. These are concrete optimization opportunities; this slice makes no memory or latency improvement claim.

The next focused performance change should reuse validated per-operation row data when calculating changes and avoid redundant receipt reopen/read validation without weakening exact inventory or authentication. Do not introduce a cross-operation key/state cache or raise capacities as part of that optimization.
