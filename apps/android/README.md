# Penny Offline for Android

Independent Kotlin / Jetpack Compose development app. Application ID `ca.penny.offline.dev` deliberately does not replace the published Flutter app. Core records remain local and work without an account, network, or generative model. No Firebase account, Penny API, or cloud AI call is used by the native core. Optional private Drive backup uses Google authorization and Internet permission behind an explicit opt-in and signed-build configuration guard; SDK operational metadata needs the separate traffic review described below.

## Build and run

Requires JDK 17+, Android SDK 37.0, NDK 28.2.13676358, CMake 3.22.1 and an Android 8+ device or emulator. Open this directory in Android Studio, or run:

```sh
# From the repository root; Node 22 is required for source authentication.
export ANDROID_HOME="$HOME/Library/Android/sdk"
mkdir -p packages/offline-crypto/.build
python3 scripts/offline/prepare-app-crypto.py android \
  --output "$PWD/packages/offline-crypto/.build/app-android-local" \
  --ndk "$ANDROID_HOME/ndk/28.2.13676358" --with-test-assets
export PENNY_SODIUM_OUTPUT="$PWD/packages/offline-crypto/.build/app-android-local/native"
export PENNY_V4_TEST_ASSETS="$PWD/packages/offline-crypto/.build/app-android-local/test-assets"
export ORG_GRADLE_PROJECT_pennyV4TestAssets="$PENNY_V4_TEST_ASSETS"
cd apps/android
./gradlew :app:assembleDebug :app:testDebugUnitTest
./gradlew -PpennyTestSandbox=true :app:connectedDebugAndroidTest :app:lintDebug
sh verify-process-persistence.sh
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n ca.penny.offline.dev/ca.penny.offline.MainActivity
```

Gradle 9.5, AGP 9.3.1, Kotlin 2.4.10 and stable Material3 1.4.0 are pinned. Compile/target SDK is 37. Android 17/API 37 with 16 KiB pages and Android 8/API 26 ARM64 with 4 KiB pages are tested locally. Hosted CI and physical-device matrices remain separate gates. Theme uses native Material components, generous rounded surfaces, accessible type, light/dark modes and system insets. No alpha Material UI is required.

## Implemented development slice

- Local CAD expense create, edit, delete, search, month totals and category summaries; explicit empty/error states.
- Native Finance tab with historical month selection, category budgets and rollover, income sources and explicit received payments, savings goals and contributions, recurring templates with due review, deterministic category reports, and explicit readable CSV export. Expected income and savings plans never become cash automatically. Reference records can be deactivated while their history remains.
- Integer minor-unit money, exact Gregorian dates and shared CRA categories. Shared contract is `packages/offline-contract`.
- SQLite in `noBackupFilesDir`, with each row encrypted using a random AES-256-GCM data key wrapped by Android Keystore. Random nonce per write, record ID/domain as authenticated data. The wrapped data key and existing-row migration commit together in SQLite; missing/corrupt key material fails closed. Every operation authenticates the current wrapped key inside its transaction; no cross-operation key cache trusts provider-specific key equality. SQLite exposes IDs/counts but no expense text or amounts. Queries decrypt in memory, so this initial schema is designed for at most 10,000 records.
- CameraX 1.6.2 captures through an in-memory callback; no plaintext photo output file is created. The picker prepares static JPEG/PNG/HEIC input up to 20 MiB and 100 million declared pixels with a sampled 2048-pixel decode. Valid existing receipt bytes are untouched. Large or supported HEIC images become a bounded JPEG, visibly labelled and previewed as an optimized copy before Save. HEIC conversion requires API 28+; Android 8 requires JPEG/PNG.
- Bundled ML Kit Latin receipt OCR, followed by the exact shared capture-v1 parser with explicit en-CA/fr-CA selection and manual review. Duplicate totals, foreign currencies, refunds and ambiguity have visible review reasons; original OCR text is available unchanged in the draft, including oversize text that yields no proposal. Valid static PNG/JPEG images are retained with the expense in encrypted SQLite records; OCR failure still allows manual details with the original image. Images can be viewed and removed independently. A scan result cannot reopen a cancelled draft.
- ML Kit Gemini Nano Prompt beta4 capability check and optional grounded category proposal when already available. Strict model JSON must have exactly four nullable fields and cannot invent a merchant/amount or act on text; schema and source-evidence checks reject malformed or ungrounded responses while retaining the draft. Unavailable/download-required/downloading states are explicit. No automatic model download or cloud AI fallback exists. Real supported-device inference still needs validation; emulator status does not prove device support. AICore itself may require online setup before its model can run offline.
- Portable encrypted backups represent schema3 records and include expenses, receipts, budgets, income sources/entries, savings goals/contributions and recurring templates, with strict v1/v2 upgrades retained. Bounded receipt input (2 MiB each, 8 MiB total, 100 receipts; dimensions at most 4096 each/16 million pixels), hash/ownership checks, complete PNG chunk checks and native image decoding precede preview and atomic SQLite replacement. Receipt ciphertext reads use 256 KiB chunks to avoid SQLite CursorWindow overflow. Restore checks the previewed vault revision and refuses intervening changes. Missing-key checks include finance-only vaults. Keys are separate from the encrypted file and are never saved in activity state or preferences. Export requires hidden-key re-entry and persists only a confirmed key encrypted under a separate Android Keystore alias in noBackupFilesDir. Missing confirmation keys fail closed on read and allow explicit re-entry of a separately saved key. Recovery dialogs enforce secure windows, password inputs and a sensitive clipboard marker with owned-content cleanup.
- Android system cloud, device-transfer and cross-platform transfer cannot silently back up the vault because it lives in `noBackupFilesDir`; backup rules also exclude app storage. Release windows prevent screenshots; debug screenshots are enabled for UI verification.

## Backup boundary

The Files document picker can save encrypted `.pennybackup` files to Google Drive **if the installed Drive app exposes a document provider**. This is user-directed file export; it is separate from direct Drive `appDataFolder` backup and is not scheduled backup or sync. The selected provider handles uploads. Export encrypts first, stages only sealed bytes in protected app storage, flushes/syncs/reopens/authenticates them, writes the selected destination, then reads it back for exact byte and authentication checks. Success means that file was verified, not that a remote upload was independently verified. Providers that refuse required write/readback operations report failure; an incomplete destination may remain for the user to remove. Losing the recovery key makes the backup unrecoverable. Files export now uses the streamed v4 container for all current schema3 domains; legacy v1–3 imports and the existing cloud-v1 path remain compatible. Verified migration from the legacy release remains a separate gate.

These two phases intentionally skip in the ordinary suite; the script is a separate required gate.

The full provider matrix, process-death during a write, actual disk-full behavior and physical-device recovery remain separate unverified gates. API 28+ rejects partial images through ImageDecoder; API 26-27 uses bounded BitmapFactory plus complete PNG framing/CRC checks and still requires its own device matrix.

P4 validation adds shared finance goldens and malformed fixtures, historical recurrence/rollover/CSV cases, finance-only key loss, v2 SQLite migration, full-domain backup roundtrip, idempotent atomic posting and rollback, and a native UI journey through budget/income/savings/recurring/report/edit/deactivation/CSV. See `evidence/P4.md` for exact commands and boundaries. Financial authority uses integer cents; threshold/progress products use BigInteger. CSV formula protection includes Unicode whitespace and BOM. New actual-payment/contribution amounts begin blank and require explicit entry.

Local command logs and screenshots live under `evidence/` and Gradle reports under `app/build/`. The checked-in `evidence/interoperability/ios-produced-v2.pennybackup` is synthetic golden data encrypted with the public fixture key, never user data.

P3 adds the exact 22-case shared receipt corpus, model-output rejection, actual camera permission denial with manual entry, synthetic HEIC and bounded photo preparation, cancellation/OCR failure, protected key mismatch/loss/re-entry, encrypted staging/write/readback faults and external Files-picker cancellation. ## Optional private Drive backup (P5 development slice)

The native Your vault panel enables private Drive only after a confirmed recovery key is re-entered and the user explicitly chooses a Google account. Every manual backup action reauthorizes using Google Identity `AuthorizationClient` 21.6.0 with only `https://www.googleapis.com/auth/drive.appdata`; `about.get?fields=user(permissionId)` supplies an opaque account binding. No account email, token, plaintext financial record or recovery key enters remote names or manifests. Access tokens are memory-only and the SDK token cache is cleared on cancellation, disable and completed actions.

Build properties `pennyDriveAndroidClientId` and `pennyDriveSigningSha256` default empty. They populate `BuildConfig.DRIVE_ANDROID_CLIENT_ID` / `DRIVE_SIGNING_SHA256` and manifest metadata `ca.penny.offline.DRIVE_ANDROID_CLIENT_ID` / `ca.penny.offline.DRIVE_SIGNING_SHA256`. The installed signer must match the configured lowercase SHA-256 fingerprint. The external Google project must enable Drive API and register the actual Android package plus its signing SHA-1, OAuth consent and any tester/verification requirements. No server client ID, client secret or backend refresh-token flow is used. These configuration fields do not establish that console registration or real consent works.

The provider creates unique encrypted snapshot and manifest objects. Resumable creation supports the portable 20 MiB envelope; subsequent PUT is restricted to the newly returned exact-host Drive upload session, never an existing file resource. All redirects and custom global cookie handlers are refused. Snapshot and manifest are each downloaded and checked byte-for-byte, by SHA-256 and by authenticated decryption before last-good is advanced. The four-phase reducer checks account, vault, recovery-key state, session epoch, cancellation and a ten-minute operation expiry around every await. A durable encrypted publication revision is reserved per attempt, preventing retry/unchanged-vault revision conflicts. Local data revision is recorded separately. Encrypted cloud settings preserve prior ciphertext on write/readback failure and fail closed after an interrupted unverified write.

Clean-device discovery uses the separately saved key and explicitly selected account. Complete pagination is mandatory: at most ten 100-item pages, 1,000 total objects and 100 manifests, counting unknown objects. Duplicate IDs/names/tokens or incomplete listings are refused. Unauthenticated or invalid individual manifests are excluded with a visible count; transport/account failures stop discovery. The chooser shows each vault, writer and revision without choosing a cross-writer winner. Before upload, inventory must have room for another two objects and one manifest; nothing is automatically deleted. Concurrent independent writers can still race at capacity, which remains a retention/protocol limitation.

A selected cloud restore verifies complete snapshot records and receipt decodes, then rechecks the account, key, epoch and local preview revision immediately before atomic replacement. Restore changes a durable local vault incarnation so an old Drive binding cannot silently resume. Manual file restore has the same local revision guard. P5b adds an explicit default-off automatic backup toggle using WorkManager 2.11.2. A unique periodic request checks roughly daily when connected and battery is not low; Android can delay it and no exact time is promised. It skips unchanged data before authorization, uses silent existing consent only, and stops for foreground attention when consent/account/key/configuration or capacity needs review. Transient retries are limited to three attempts with exponential backoff and an eight-minute coroutine deadline. A shared process lease preempts background work for foreground actions; durable settings, independent stop markers and atomic snapshot/revision capture prevent failed opt-out writes, late callbacks or a second database connection from falsely advancing backup status. A failed stop/retry settings write leaves automatic work stopped until explicit successful re-enable. Scheduling intent is reconciled after restart. See `evidence/P5b.md`.

The manifest uses default-deny platform TLS with a dedicated non-public CA certificate (private key discarded) and system trust only for exact `www.googleapis.com`, with cleartext disabled. The only app-owned HTTP adapter uses fixed Drive paths. An opt-in, credential-free instrumentation probe confirms the Drive TLS path and rejects platform TLS to `firebaselogging-pa.googleapis.com`. This is defense in depth, not proof against SDK custom/native networking or traffic to the same allowed host. ML Kit documents operational analytics/device metadata collection; no complete supported standalone opt-out was found. Real final-SDK/AICore traffic observation and accurate Data safety disclosure remain release gates.

P5 validation and exact evidence are in `evidence/P5.md`. Run the separate network probe only when desired:

```sh
adb shell am instrument -w -r -e class ca.penny.offline.NetworkBoundaryTest -e pennyNetworkProbe true ca.penny.offline.dev.test.test/androidx.test.runner.AndroidJUnitRunner
```

## P6 platform, display and scale checks

The original Penny coin/P asset supplies adaptive and monochrome launcher resources. Navigation uses vector icons; finance months have accessible previous/next controls, localized Gregorian month labels and optional explicit YYYY-MM entry. Large text uses two rows of navigation items, wrapped receipt-language controls, and an inline Add expense action. Reports and vault content stay bounded on wide screens. Your vault displays record/receipt/byte capacity; full-vault errors advise exporting and verifying a backup before removing data.

`verify-display-matrix.sh` uses an isolated emulator and the test package, exercises month minimum/maximum bounds and restores default dimensions plus prior font/night settings. Screenshots and raw performance values are under `evidence/`; see `evidence/P6.md` for exact measured scope and outstanding release gates. The opt-in `PerformanceDeviceTest` measures 1,000/10,000 expenses and four exact 2 MiB receipts. It uses unique test databases and keys, never the development vault. Per-row hardware calls were replaced with the wrapped data key after the measurements exposed repeated save/open delays; the strict number parser now scans tokens linearly. Neither change alters portable wire formats.

Production packaging is explicit: `-PpennyRelease=true`, `-PpennyVersionName=3.0.0`, an externally checked fresh `-PpennyVersionCode`, and both public Drive configuration properties. That profile uses `com.penny.penny_mobile` and cannot combine with the test sandbox. Release signing is configured only when all four environment fields are supplied: `PENNY_ANDROID_KEYSTORE`, `PENNY_ANDROID_KEY_ALIAS`, `PENNY_ANDROID_STORE_PASSWORD`, `PENNY_ANDROID_KEY_PASSWORD`; partial configuration fails. No signing secrets belong in Gradle command-line properties. With no signing environment, the build remains unsigned and must fail release preflight. The embedded Drive signer is the installed-app registration certificate; it may differ from the upload-key certificate. Root packaging owns store version/signature/configuration preflight, not this development profile.

## V4 app integration

The app and prototype compile the same Kotlin/JNI codec sources. The reader applies current ledger limits and validates authenticated logical input. Native v4 writers and guarded restore candidates are connected to Files; direct cloud-v1 publication remains separate and does not yet use v4 file transport. [App-reader evidence](evidence/v4-app-reader.md) records exact tests and boundaries. Native dependency preparation authenticates and builds pinned source into a new output directory; choose a new path for a fresh preparation. Normal app builds need only `PENNY_SODIUM_OUTPUT`; instrumentation additionally requires the generated corpus above. The exact ISC license is bundled as an app asset.

[Writer/restore integration](../../docs/offline/V4_EXPORT_INTEGRATION.md) and [Files export evidence](evidence/v4-files-export.md) distinguish focused runtime tests, real local picker saves, preserved failures and physical/cloud gates. The Files result belongs to one opaque export request; stale results cannot consume a replacement request.

[Receipt-free live state](evidence/live-state.md) serves ordinary open/list/view-one and existing-expense metadata edits. Full sequential authentication remains. Receipt-changing, finance and legacy/cloud operations explicitly retain complete Snapshot compatibility at existing limits. The caller audit and focused native checks record the exact scope; no resource improvement or larger-capacity claim is made.

[Current-cap v4 repair](evidence/v4-repair.json) validates a backup before explicit replacement when the receiving local key is missing or encrypted state is corrupt. Preview never provisions a key; installation binds actual source/key ownership and reuses guarded replacement. Repair alone uses bounded complete Snapshot hydration. Platform-specific limits, failed runs and exact tests remain in the report.
