# iOS explicit Files v4 repair

Files restore can now preview and explicitly replace a receiving vault whose device key is missing or whose current encrypted pointer/receipt cannot validate. The healthy receiving path still uses its original receipt-streamed candidate. Repair alone uses a complete, bounded compatibility Snapshot after the actual native v4 reader has accepted every record/image, authenticated FINAL/EOF, closed input, checked ciphertext length/digest and enforced exact existing export capacity. No plaintext file is written.

Repair authority is captured before acquiring the backup. It binds the same receiving owner/local revision/writer/restore incarnation, pinned root identity, raw encrypted pointer and original metadata/receipt namespace fingerprints. Descriptor-relative reads hash ciphertext incrementally in 64 KiB chunks and bind file/directory identity, type, owner, permissions, size and timestamps. Changes to metadata or receipts with an unchanged pointer also reject. The prepublication check excludes only exact new names created by the same publication and verifies its managed rollback copy. Unknown regular entries are bound; unsafe links, deeper unknown directories and files exceeding the existing 32 MiB local-read bound refuse without cleanup of those entries.

Preview never creates a key. Explicit Replace rechecks the original key observation, treating only the specific missing-key result as absent. Repair uses atomic create-only `SecItemAdd`; an alias appearing at that boundary is refused rather than adopted. Existing inaccessible/locked errors remain failures. The existing `PreparedVaultWrite(restoring: true)` and durable commit/publish/reopen/rollback protocol performs replacement on the worker. A newly created owned key may remain after a later failed installation; originals remain unchanged and a fresh explicit preview can retry with it. This is not a full key-state rollback, and no foreign key is removed.

## Current proof

`apps/ios/.build/v4-repair/Tests02.xcresult`: **27/27 passed, 0 skipped** on isolated `ca.penny.offline.v4repair`, F70 iPhone 16e / iOS Simulator 26.4.1. Build05 and the exact source, app runtime dylib, launcher, unit executable and static module were frozen before testing in `artifacts/offline/v4-repair-ios/validation-02/provenance.json`.

Seven new repair methods cover missing-key preview/no provisioning/confirmed exact reopen; corrupt pointer and receipt; wrong recovery key, truncation, trailing/pattern data, cancelled acquisition and closed preview; inaccessible key refusal; pointer/metadata/receipt/root and key changes; foreign receiver and single-use ownership; injected failed publication and actual Task cancellation after publication, with original bytes retained and retry; and unchanged healthy candidate behavior. The creation-race regression inserts a foreign key inside the creator boundary. A separate actual simulator Keychain call proves `SecItemAdd` refuses an existing alias without changing it.

The run also includes FilesRestoreTests (6), V4CandidateTests (7), original receipt persistence/legacy backup/restore/delete, recurring finance idempotency, both requested cloud compatibility methods, actual v4 finance/receipt export/install, 10,000-expense refusal usability and current receipt count/aggregate capacity checks. The opposite-native Android fixture is compared through all eight arrays, exact vault/snapshot identity and raw receipt bytes after fresh-store reopen. The shared seven acceptance IDs and exact hashes are mapped in `v4-repair.json`.

Tests01's earlier 26/26 run is preserved separately. Independent review subsequently identified that its generic create-or-load API could adopt a key arriving after the missing observation; the final atomic-creation fix and new regression were both included in Tests02. Initial compile diagnostics are retained in build01/build02 logs. No runtime test failed in either executed suite.

## Limits

This is current-cap, repair-only compatibility hydration; no capacity, wire/private crypto or cloud change. Raw namespace capture/recheck is synchronous on the store actor; incoming v4 processing and confirmed preparation/publication run on the worker. A long retained metadata history can make inventory expensive; no performance claim is made. The next metadata-retention work was not included.

Injected write/checkpoint failures are not real disk-full or power-loss tests. This run does not establish physical-device Keychain/protection behavior, full UI/accessibility or release readiness. Existing publication may retain unactivated encrypted metadata or quarantined receipt bytes after failed writes. F70 is shut down and the normal demo was untouched. Estimated total work was approximately 18k–20k tokens including the two required review corrections, not a tool-metered count.
