The actual storage path now uses detached receipt files at the existing 10,000-expense, 100-receipt and 8-MiB receipt limits. Portable backup versions 1–3 and the bounded in-memory `VaultSnapshot` API are unchanged. [durable-storage.json](durable-storage.json) contains exact source/fixture/evidence hashes, commands, runtime details and a method-by-method map of the 14 shared lifecycle scenarios.

**Validation:** 49/49 focused native tests pass (7 durable storage, 9 receipt foundation, 18 vault, 11 cloud, 4 archive worker). The dedicated process writer and reader each pass 1/1; the tests assert distinct application PIDs, 12207 and 12223. An unsigned generic iPhoneOS Release build passes. F70 was the only simulator used and was shut down afterward. Full UI/hosted CI is a separate integration check.

The fresh-process pair records a valid pending replacement and a replacement with a tampered receipt, then exits the writer test process. The reader process authenticates the valid replacement and restores the authenticated predecessor for the invalid replacement. These are actual separate processes with checkpoint-created interrupted states, not SIGKILL or physical power-loss tests. Staged, verified and journal-cleared interruption cases additionally run through new store instances. Missing-key behavior uses an injected device-key reader; no platform Keychain item was deleted.

## Private on-disk format

The trusted `PennyOffline` root is private and excluded from OS backup. Descriptor-relative file operations and a directory-inode `flock` lease serialize all store instances. Root provisioning occurs before the storage context is exposed; a legacy inline root has a narrow one-time adoption path. New files use the compile-time filesystem policy: simulated protection on simulator, actual class-A protected creation and descriptor readback on device. Physical-device protection remains unverified.

- `vault-v1.pennyvault`: reserved `PENNY-DURABLE:POINTER:1\n` prefix followed by CryptoKit AES-GCM combined bytes. Closed encrypted JSON contains `version:1`, `storeId`, `current:{id,sha256}`, `previous:{id,sha256}|null`, and `journal:base64|null`. AAD is `PENNY-LOCAL-POINTER:1`. Unknown durable subtypes fail closed; unmarked old inline encrypted files retain their original reader.
- A generated `<id>.pennygen` metadata file: `PENNY-DURABLE:RECORD:1\n` prefix followed by AES-GCM. Closed payload contains `version:1`, `storeId`, `generationId`, `metadata:{writerId,revision,restoreEpoch}`, `body` (base64-encoded unchanged schema-3 JSON with an empty attachments array), and closed seven-field receipt descriptors. AAD is `PENNY-LOCAL-GENERATION:1` + NUL + store UUID + NUL + generation UUID. References authenticate the exact ciphertext SHA-256. Metadata/previous-copy reads are bounded to 32 MiB; the existing portable plaintext/export limits still apply to every hydrated snapshot.
- The optional journal inside the pointer is separately encrypted using AAD `PENNY-LOCAL-JOURNAL:1` + NUL + store UUID. Its closed payload binds `currentHash` and `previousHash|null`. Pointer publication and pending status therefore change in one atomic file replacement. A previous-reference file preserves the exact old pointer or legacy ciphertext; `vault-rollback.pennyvault` also retains the predecessor bytes.
- Each changed receipt gets one privately generated immutable group with exactly one `<receipt-id>.pennyreceipt`. Its existing `PNYRCP01` format is unchanged. Ordinary edits reuse matching authenticated descriptors/files; explicitly verified restore creates fresh groups so it can repair damaged cached receipt references. No plaintext receipt is written to disk.

Prepared writes bind the source ciphertext digest, store incarnation, writer, revision and restore epoch. These are checked against the actual directory under its lease. All domains and references validate before publication; receipt inventories and authenticated candidate bytes are rechecked after preparation callbacks and before publication/verification completion. A cancelled published task uses a noncancellable rollback primitive with the same filesystem/sync checks. Missing live metadata alongside existing generation/rollback/unknown data locks the vault rather than initializing an empty ledger. Explicit verified backup recovery remains available after missing-key failure because the encrypted source digest is captured before key loading.

Async app writes perform file preparation, native image validation, hydration and commit on `ArchiveWorker`. Initial load and existing synchronous compatibility methods remain synchronous. The initial API still hydrates receipt base64 and retains the previous preparation buffers, so this is not a streamed-memory or performance-improvement claim. A failed async commit conservatively closes the store until reload, including cases whose predecessor was restored.

## Lifetime, migration and remaining gates

Closing a committed read/export lease releases descriptors and shared directory locks; it never deletes committed bytes. Explicit conservative GC preserves active, immediate predecessor, pending and reader-pinned groups. It reclaims only authenticated unreferenced receipt groups, preserving unknown/replaced entries and metadata provenance. It does not compact metadata files. New groups remain owned during preparation; durable ownership transfers immediately before potentially successful pointer publication. Uncertain publication can retain encrypted inactive state for later conservative cleanup.

Legacy data migrates on the next successful mutation or publication-identity write, preserving the old ciphertext until authenticated replacement succeeds. The shared previous/replacement inputs exercise every finance domain, IDs, totals and original receipt bytes. The seven durable tests additionally cover second-instance stale writes, repeated-revision recreation, receipt repair, established corruption refusal, cancellation rollback, GC pinning and unknown-file preservation.

Run the ordinary focused suite through `PennyOffline`. The `PennyOfflineDurableProcess` scheme is intentionally separate: invoke only `DurableProcessTests/testFreshProcessWritePending`, then invoke only `testFreshProcessReadPending` in a second `xcodebuild test-without-building` command. Exact working argv are recorded in the JSON; running both methods in one invocation is not a fresh-process proof.

No physical lock-state, real disk-full, power-loss, signing, store release, new v4 backup reader, memory benchmark or increased-capacity claim is made. The earlier isolated foundation evidence remains a historical checkpoint; the current integrated source hashes are in this report's JSON.
