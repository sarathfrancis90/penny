# Penny Offline - native iOS

Independent SwiftUI development app, bundle `ca.penny.offline.dev`, deployment target iOS 26.0. It does not replace the shipping Flutter app or contact the Penny API/Firebase. This is a local personal-finance development build for the next major release, not an App Store release candidate.

## Run and test

Requires Xcode 26 and XcodeGen. The checked-in project is generated from `project.yml`.

```sh
cd apps/ios
xcodegen generate
# Seed the public synthetic receipt into your booted test simulator.
xcrun simctl addmedia booted ../../packages/offline-contract/fixtures/receipt.png
xcodebuild -project PennyOffline.xcodeproj -scheme PennyOffline \
  -destination 'platform=iOS Simulator,name=iPhone 17,OS=26.4.1' \
  -derivedDataPath .build -parallel-testing-enabled NO test
```

Keep normal simulator ad hoc signing enabled: `CODE_SIGNING_ALLOWED=NO` removes the simulated entitlement needed by Keychain and the app correctly refuses to open its vault. Device builds require a signing team.

Local artifacts are under `.build/`. The receipt UI test expects the seeded public fixture above. Captured cross-native runtime archives under `packages/offline-contract/fixtures/native-exports/` are mandatory test inputs, with runtime and checksum provenance; they are not skipped when a local build artifact is absent.

`ArchiveWorker` owns serial encrypted archive preparation, strict restore decoding and coordinated Files reads/writes. It also prepares validated, encoded and encrypted immutable vault writes. ## Implemented

- Native system navigation, tabs, sheets and controls adopt Liquid Glass on iOS 26. Semantic colors, Dynamic Type, search, accessible labeled controls, empty and failure states.
- CAD expense creation, editing, deletion, civil dates, exact integer cents, canonical category strings, local search and monthly total.
- AES-256-GCM encrypted local snapshots, independent random key in `WhenUnlockedThisDeviceOnly` Keychain, complete file protection, atomic writes and exclusion from automatic OS backup. Failed decryption never silently creates an empty vault or permits normal writes.
- App-switcher privacy cover while inactive. This is not a biometric app lock.
- Apple Vision receipt text recognition on device; exact deterministic receipt parsing with explicit English (Canada) or French (Canada); optional Foundation Models category suggestions bound explicitly to `SystemLanguageModel.default` and validated against source evidence. No cloud fallback. Unsupported hardware, disabled Apple Intelligence and unavailable models have explicit states. User reviews every suggestion. Original static JPEG/PNG receipts are retained unchanged inside the encrypted vault, linked to their expense, and can be viewed or removed. Supported JPEG/PNG originals are never changed. HEIC and larger static images (up to 20 MiB / 48 megapixels) are prepared in memory as a bounded JPEG with location metadata removed, and require an explicit optimized-copy preview/acceptance; that saved JPEG is not the original input file. Animated PNG, damaged images and excessive input size are refused.
- Encrypted `.pennybackup` export to a user-selected Files folder, including iCloud Drive if available, and restore with a separate random recovery key. Full exact key re-entry plus device-only Keychain write/readback is required before export. Recovery keys use a separate Keychain service from the local vault key; failed readback rolls back the prior key. Export staging is protected, excluded from OS backup, flushed, reopened and authenticated. Each destination has a fresh UUID filename created with exclusive no-overwrite semantics, then coordinated bounded readback/authentication before export success. Cancellation removes protected staging. Failed new exports cannot overwrite earlier backups. Restore authenticates, checks the complete schema and shows replacement counts before atomic replacement. Recovery is available even if the existing local vault cannot be opened.
- Portable snapshot schema 3 retains all receipt bytes with owner IDs, byte counts, SHA-256 hashes and canonical base64. Schema 1 and 2 snapshots upgrade with empty finance arrays and explicit new expense defaults, retaining all prior fields and receipt bytes. Per-receipt bounds are 2 MiB, 4096 pixels per side and 16 megapixels; the vault allows 100 receipts and 8 MiB of original receipt data, subject also to the 15 MiB plaintext/20 MiB encrypted-envelope cap. Over-capacity changes fail before saving.
- Native camera capture supplies an in-memory image for optimized-copy review and never writes to the photo library. Camera denial/unavailability leaves manual entry and photo/file attachment available. The simulator explicitly reports camera unavailable; physical camera capture remains a device gate.
- Receipt parsing preserves the full source text, scalar bounds, original line indexes and ordered refusal reasons. Ambiguous/foreign/signed totals remain absent; model output cannot invent merchant or money. Category suggestions preserve manually corrected fields even after failure or cancellation. Every draft requires explicit Save; cancelling processing or the editor cannot post an expense.
- Plans screens provide monthly category budgets with rollover and thresholds; income source settings plus actual received entries; savings goals plus actual contributions; and recurring expense templates with explicit review/post actions. Sources, goals and templates can be deactivated while their history remains intact. Required new amounts are blank, and actual entries never default to invented money.
- Deterministic Gregorian recurrence clamps each month independently, including leap years and historic dates. Income and expense occurrence references commit atomically with their entries; retries return the existing entry. Due review is limited to the selected month through the current local civil date. Scheduled amounts do not enter actual cash totals.
- Reports include monthly received income, expenses, net cash, savings allocations, and income/expense categories. Civil month entry supports years 0001–9999. CSV export requires an explicit readable-data confirmation and protects spreadsheet formula prefixes, including Unicode whitespace. CSV contains expenses only; encrypted backups contain every finance domain and receipts.
- Encrypted staging is flushed, reopened and validated before atomic replacement; the previous encrypted generation remains in `vault-rollback.pennyvault`. Live and rollback files are flushed. Caught failures preserve the previous complete generation and failed rollback closes the vault. Restore previews track the live revision so stale previews cannot overwrite subsequent edits.
- Shared Node/native golden archive compatibility, duplicate and unknown JSON member rejection, bounded archive reads, authenticated encryption, calendar/amount validation and persistent CRUD tests. XCUITest covers create, relaunch, edit, delete and relaunch using real device-key storage.
- Strict shape inspection and schema upgrades decode the original JSON bytes through Codable, preserving Unicode values and member names, including leading U+FEFF. Schema 3 never fills missing required fields during a legacy upgrade.

The backup wire contract and public fixture keys are under `packages/offline-contract`; public fixture keys must never protect user data. Local encryption and backup encryption use independent keys and distinct authenticated context strings.

## Optional CloudKit backup

The default project and every simulator build refuse to construct `CKContainer`. A separately signed cloud build must define `PENNY_SIGNED_CLOUDKIT`, set the Boolean Info.plist member `PennyCloudKitSignedBuild` to true, and provide `PennyCloudKitContainerIdentifier` with the configured `iCloud.` container identifier. These are configuration guards, not entitlement proof. Before distributing any enabled build, host preflight must inspect the actual signed application/provisioning entitlements for application identity, CloudKit service, container and environment. No private Security APIs or unsigned-profile parsing is used. Container provisioning, private database schema and a real-account restore drill remain external gates.

`CloudKitTransport.swift` is the sole remote adapter and uses Apple's CloudKit framework, with no third-party network dependencies. It writes immutable `PennyEncryptedObject` records in the private database, using record IDs equal to the portable object filenames, an encrypted `payload` CKAsset and an integer `byteCount`. The schema must support the complete bounded record query. New records use `.ifServerRecordUnchanged`; each per-record result is checked. No delete or mutable latest record exists. Explicit private-database fetches retrieve and authenticate the snapshot and manifest bytes before the encrypted local last-good status advances. Fetching byte-count metadata first reduces accidental oversized transfers; CloudKit itself allocates/downloads the asset before the app's bounded read, so this is not proof of a strict SDK transfer allocation limit.

The shared manifest v1 contract is separate from unchanged portable snapshot schema 3. Account tags use the opaque CloudKit user record identity. In-process account epochs, recovery-key fingerprints, operation cancellation and restored-vault epochs are checked around suspension points. A local-only encrypted frame persists writer identity, revision and restore epoch atomically with financial data; old local snapshots upgrade without changing their Unicode or portable fields. Every publication attempt reserves a durable revision first, including retries after uncertain completion. Edits made during an upload remain pending. Restoring a backup invalidates the old cloud binding and requires explicit re-enablement.

Discovery lists at most 10 pages, 100 items per page, 1,000 total objects and 100 manifest candidates. It rejects incomplete/ambiguous inventories, authenticates candidate manifests, groups history by vault and writer, and requires explicit selection plus a fresh revision-checked restore preview. Before publication, the same complete inventory must contain at most 99 manifests and 998 total objects, reserving space for two new immutable objects. It never deletes history to make room. Concurrent writers can race between inventory and upload; no server-side capacity reservation is established by this slice.

The manual UI requires a confirmed recovery key and explicit enablement. It displays the last verified generation, pending edits, provider errors, cancellation and grouped history. Local finances remain usable when cloud configuration, account access or connectivity is unavailable. Encrypted Files export remains separate from verified CloudKit backup.

Automatic backup is a separate, default-off opt-in with explicit consent. `BackupCoordinator` is owned once by the app and serializes both foreground operations and background callbacks through the same `CloudPublication`. `BGTaskScheduler` registers `ca.penny.offline.backup.processing` during app initialization; the compiled plist declares that identifier and the `processing` background mode. Requests require network connectivity, coalesce pending changes, and set an earliest eligibility date. A successful backup moves automatic eligibility at least 24 hours forward; transient failures may retry after one and two hours, then pause. Unchanged vaults are skipped. Earliest eligibility is not a promised execution time: iOS may delay or skip the task, and complete-protection recovery keys require the device to be unlocked.

Expiry, explicit cancellation, disablement and invalid account/key/restore state cancel pending requests and the active publication. Expired task completion is guarded against late callbacks and occurs once. Automatic opt-in and retry state are encrypted; an independently flushed and reopened protected stop marker prevents failed opt-out or retry-state writes from restoring an old enabled setting after relaunch. A successful explicit re-enable is required after such a pause. This does not establish behavior under simultaneous failure of both marker and settings storage or physical power loss. Scheduling failures, locked keys, exhausted retries and provider/capacity errors remain visible and preserve local finances and earlier remote objects.

A synthetic affirmative consent journey uses `--uitesting --synthetic-cloud` in DEBUG builds only. It injects in-memory transport and scheduling into the same coordinator, labels the screen as synthetic, and uses only the public fixture key and isolated test vault. It does not alter the real CloudKit configuration gate or submit operating-system requests; the implementation is absent from Release builds. It tests consent cancellation, enablement/relaunch and disablement/relaunch. The default-build journey separately proves that real cloud and automatic enablement remain unavailable. Public runtime cloud archive captures are shared under `fixtures/native-exports/`; tests import the Android cloud manifest and referenced snapshot, then compare every finance and receipt array after encrypted local restore/reopen.

Apple background task references: [registration before launch completes](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/register(fortaskwithidentifier:using:launchhandler:)), [earliest eligibility](https://developer.apple.com/documentation/backgroundtasks/bgtaskrequest/earliestbegindate), and [expiration cleanup](https://developer.apple.com/documentation/backgroundtasks/bgtask/expirationhandler).

The device-only configuration branch also compiles in an unsigned generic iPhoneOS Release build using `SWIFT_ACTIVE_COMPILATION_CONDITIONS=PENNY_SIGNED_CLOUDKIT CODE_SIGNING_ALLOWED=NO`, with separate derived data at `.build/device-cloud-compile` and log `.build/p5-device-cloud-compile.log`. This is a compile check, not proof of signing, CloudKit entitlement, network transfer or account access. P6 now declares all four iPad orientations and verifies the compiled product; this warning is resolved.

## Boundaries before release

- Fault injection is not a physical power-loss or real disk-full test. Simulator relaunch proves normal persistence, not arbitrary process death during a write. The encrypted rollback file is retained, but a dedicated rollback recovery UI is not implemented.
- Recovery-key re-entry, Keychain readback, protected export staging, destination verification and no-overwrite behavior have native tests. Physical lock-state enforcement is unverified: the simulator does not expose NSFileProtectionKey metadata, and the test records that limitation while requiring complete protection on device builds. Recovery drills across real devices, key rotation, reminders and external provider failure modes remain release work.

- Manual CloudKit publication/discovery/restore is implemented behind a disabled build gate and tested through a fake transport. Actual entitled CloudKit upload/readback, real account/device restore and clean-device recovery remain unverified. Optional best-effort background scheduling is implemented and fake-tested; actual operating-system wake timing and protected-key behavior still require device evidence. File export success reports export only; it does not claim remote upload completion.
- Physical-device Apple Intelligence, Vision OCR corpus accuracy, airplane-mode/network-capture verification and physical assistive-technology testing need release evidence. Simulator iPad/large-type journeys are covered above; unfiltered accessibility diagnostics remain unresolved. Simulator support cannot prove hardware AI inference.
- The bounded encrypted JSON snapshot implementation rewrites the vault per edit. Every save validates receipt images and rewrites the bounded snapshot. P6 measures the current bounds and moves expensive preparation off MainActor as described above. A database/storage migration and fresh measurements are required before scaling beyond these limits.
- Refunds/multicurrency, legacy export/import migration, recovery-key rotation, app lock, recovery reminders, final store privacy declarations and release signing remain phased work. The original native icon and required-reason privacy manifest are included.
- The production bundle/listing transition must be settled with migration evidence. The development bundle intentionally coexists with the installed app.
