# Offline capture proposal contract

Frozen parser version 1, 2026-09-13. Source: `packages/offline-contract/receipt-parser.mjs`; synthetic native corpus: `fixtures/receipt-parser-corpus.json`. This contract prepares editable suggestions and never writes an expense, triggers a tool, or accesses a network. Receipt bytes are retained independently of OCR/model success under the receipt backup contract. Manual entry always remains available.

## Exact proposal

Every successful parser call returns exactly `parserVersion:1`, `locale`, `sourceText`, `merchant`, `amountMinor`, `currencyCode`, `merchantLineIndex`, `totalLineIndex`, `category:null`, `requiresReview:true`, and `reasons` (ordered array of stable strings). Merchant is trimmed source text or null. Amount is positive CAD integer cents or null. Currency is CAD only when amount is present, otherwise null. Evidence indexes are zero-based original source lines, retaining blank-line positions; null means no accepted evidence. The original sourceText remains byte-for-byte/string-for-string unchanged. Fields with null are not silently filled from a generative response.

The caller explicitly selects `en-CA` or `fr-CA`; there is no device-locale guessing. Input is limited to 4,000 Unicode code points, with valid Unicode scalar sequences. Oversize input throws `input_too_long` before proposing anything; it is never truncated into an apparently complete receipt. Unsupported locale and invalid scalars throw `unsupported_locale` and `invalid_unicode`. Empty input is valid but yields missing fields. Split lines on CRLF, CR or LF; trim only for matching, preserving sourceText and original indexes.

## Merchant and amount rules

Prefer exactly one `Merchant:`, `Vendor:`, `Marchand:` or `Commerçant:` line. Multiple explicit merchant labels yield `ambiguous_merchant`. Without a label, consider only the first nonempty line; do not hunt arbitrarily through the receipt for another name. A candidate must have a letter, contain at most 200 code points, have no control characters or decimal-money substring, and not be a receipt/invoice/thank-you header, total label or ignored financial line. A labelled merchant such as `Merchant: Total Café` is allowed. Missing or rejected names yield `missing_merchant`. This is a conservative name proposal, not proof of merchant identity.

Exactly one final-total line is required. English labels: Grand Total, Total Paid, Amount Due, Balance Due, Total. French labels: Total général, Montant total, Total à payer, Net à payer, Total TTC, Total. Matching is case-insensitive and anchored to the line start; an optional colon follows the complete label. Subtotal/sous-total, tax/TPS/TVQ/GST/HST/PST, tender/cash/change, discounts and total-item/total-tax/total-discount lines are explicitly excluded. Two total lines are rejected even when amounts agree; the parser never chooses the last, first or largest amount. One total line containing multiple amounts also fails.

English money requires exactly two decimals with a period; correctly grouped commas are optional (`1,234.56`). French money requires exactly two decimals with a comma; groups may use ordinary space, tab, NBSP U+00A0 or narrow NBSP U+202F (`1 234,56`). Group positions must be exactly three digits. No OCR letter-to-digit substitutions, exponent notation, rounding, date-number extraction or locale reinterpretation is allowed. CAD, CA$, C$ and $ decorations are supported at the edges of the amount. Bare dollars or no explicit currency produce `currency_assumed_cad`, visible for review; the selected Canadian locale is an assumption, not currency detection.

Any recognized foreign currency code/symbol anywhere in the source prevents a CAD amount proposal (`foreign_currency`), including USD immediately adjacent to digits. Refund/credit-note language yields `unsupported_refund`; French remboursé is recognized. Minus, Unicode minus, plus, parentheses and CR credit notation on a total yield `signed_total`. Item-level discounts do not turn a positive final total into a refund. Zero yields `nonpositive_total`, an amount above the money cap yields `total_overflow`, and invalid format/grouping yields `malformed_total`. Absence of a total yields `missing_total`; repeated totals yield `multiple_totals`.

Instruction-like phrases such as “ignore previous instructions”, system-prompt references or execute-command requests yield only `instruction_like_text`, with no merchant or amount. This is an additional conservative signal, not a security boundary: arbitrary receipt text is always inert data, regardless of whether this small phrase list recognizes it. Native code must never dispatch actions from text/model output.

## Optional on-device models

`validateModelProposal(sourceText, locale, output)` accepts exactly `merchant`, `amountMinor`, `currencyCode`, `category`, all required and nullable. A proposed merchant must equal the deterministic evidence-backed merchant; a proposed amount must equal the single validated labelled total. Currency must be null with null amount, otherwise CAD. A nonnull category must match one canonical category and requires a valid source merchant and total. Unknown fields, invented names/amounts, unsupported categories, and attempts to fill ambiguous totals are rejected. Native callers retain the deterministic draft when model validation fails and explain that manual review is needed.

Canonical membership does not prove a category is semantically correct; classification remains an editable proposal. A category-only action must preserve manually edited merchant and amount fields, including when inference fails or is cancelled. All proposals require deliberate review and Save. Optional model absence, download state, cancellation, malformed responses or inference failure must not prevent manual entry or discard a validated receipt. No cloud model fallback is allowed.

## Corpus and verification

The 22 synthetic cases cover English/French decimals, foreign currency, signed/refunded totals, duplicate totals, subtotal/tender/change confusion, merchant names containing Total, missing/ambiguous merchants, instruction-like text, OCR O/0 confusion, malformed grouping, locale mismatch, discount/tax/item exclusions, two amounts on one line, zero, oversize input and Turkish dotted/dotless-I case-fold differences. An `inputRepeat` case describes a large input without bloating the fixture. Native tests expand it exactly and assert the named error. Other cases compare fields, reason order, evidence indexes, unchanged source text and requiresReview. Native case-insensitive regexes must not accept `Total Paıd` or `Total Paİd` as `Total Paid`; Java's default Unicode case folding differs from ECMAScript here.

The shared tests also reject ungrounded optional-model output. These tests exercise deterministic parsing only; they do not establish Vision/ML Kit OCR quality, supported-device model inference, offline first-run resources, accessibility or camera behavior.

CSV review added shared `conformance-v3.json.csvCases` for U+FEFF BOM, U+00A0 NBSP, U+202F narrow NBSP and mixed prefixes. They must be treated as whitespace before `=`, `+`, `-` or `@` and neutralized with a leading single quote before CSV quoting. Native default trim/regex whitespace behavior may differ from JavaScript; consume the exact shared cases rather than assuming parity. The raw user text in the vault remains unchanged.
