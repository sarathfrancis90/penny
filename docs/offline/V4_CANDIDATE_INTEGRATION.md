# V4 candidate integration — approved next internal slice

This specifies the next implementation; it is not implementation or runtime evidence. Existing v1–v3 wire readers/writers, product caps, provider flows and UI remain unchanged. Acceptance is recorded in `packages/offline-contract/fixtures/v4-candidate-v1/acceptance.json`; each platform must report actual methods and outcomes independently.

## Two passes over owned ciphertext

1. Before pass 1, capture an opaque receiving-store binding using the existing authenticated target/namespace/key checks. Capture must not initialize an empty vault or provision a key. Preserve iOS directory/inode, digest, storeId, writer/revision/restoreEpoch and key identity; preserve Android database/namespace/connection, activeState, revision/incarnation, restoreBinding, verified source digest and wrapped-key identity. No cloud writer field is introduced. Do not retain a write lease across decoding.
2. Acquire the encrypted input once into a newly created private, excluded-from-backup ciphertext file. Bound actual bytes during copy, hash them, sync/close and pin owned identity. Reject source read/close failure and observable acquisition mutation. Never reopen the original provider URL for the second pass. Retain a private owner/pin; recheck ownership on every reopen or rewind. An unlinked read-only owned snapshot FD is also suitable; duplicate/rewind its owned handle for passes without resolving a pathname. Each pass computes SHA-256 and actual byte count through EOF; both must equal acquisition. Cleanup may unlink only owned identities, never a replacement or unknown sibling.
3. Pass 1 uses the actual app-linked reader and mandatory native semantic/image validation. Collect bounded receipt-free domain metadata and immutable receipt declarations; discard each borrowed raw receipt after native validation. Accept this collection only after authenticated FINAL, strict EOF, successful source/sink close and post-close cancellation checks. Retain completed identity, counters, transcript digest and policy byte totals.
4. Recheck the original opaque target binding under the existing preparation lease, then call the existing bound candidate preparation API with the collected body/declarations. Do not silently recapture a newer target after pass 1. Reuse its exact encoded candidate capacity calculation, including JSON escapes and base64-equivalent receipt sizes, in addition to app-reader metadata/count limits. A v4 validation summary alone does not establish schema3 exportability or candidate capacity.
5. Pass 2 fully validates the same owned ciphertext again. Reconcile metadata/declarations against pass 1 and supply each complete, authenticated, native-validated borrowed receipt directly to preparation. Retain at most one raw receipt; never build aggregate receipt base64 or plaintext receipt files. Compare both complete summaries/transcripts and exact ciphertext digests/counts. Only after the reader returns successfully, including close and post-close cancellation, call preparation `finish`. A provisional sink completion callback cannot finish or publish a candidate.
6. Return only the existing opaque, same-owner candidate plus immutable preview summary. Installation uses the existing guarded publication/rollback/reopen path and a fresh existing-device-key lookup. It cannot convert public metadata or a caller assertion into install authority. Prepublication failure/cancellation discards only owned inactive data. Successful or uncertain publication retains potentially referenced bytes; claim previous preserved only after confirmed rollback. Existing one-shot, foreign-owner and GC-pin rules apply unchanged.

The recovery root decrypts the archive; the existing device root encrypts local receipts. Neither is persisted in the ciphertext spool, and they are never substituted for one another. This slice requires an established ready target; missing-key repair/new-vault onboarding is separate. Candidate preparation avoids an aggregate receipt graph; existing bounded live snapshot hydration after install is not redesigned or claimed streaming here.

## Minimal source seams

- iOS: a mandatory-native-validation observer on `packages/offline-crypto/apple/module/PennyV4Reader.swift`, app coordination beside `V4ReadOnlyAdapter.swift`, and opaque pre-pass capture/recheck beside `VaultStore.beginLocalReceiptReplacement`. Reuse `DurableVaultStorage.Preparation` and `installLocalReceiptReplacement`.
- Android: a collecting/forwarding sink beside `V4BackupReader`, opaque capture/recheck beside `VaultStore.beginReceiptPreparation`, and existing `installPrepared`. `finishUncommitted` remains provisional; finish the candidate after `decode` returns.
- Both: use existing frame/logical crypto implementations and exact native validators. No production writer, alternative parser, public fake-FINAL flag or plaintext spool. Use the current reader limits and the existing 20 MiB encrypted-input ceiling; do not increase admission to Profile A.

A one-pass design would need encrypted provisional receipt staging before all declarations exist, followed by authenticated adoption or re-encryption and another cleanup protocol. Two passes reuse existing candidate ownership at the cost of a second bounded decrypt/native decode and one ciphertext spool. Provider account/session guards, UI confirmation, background execution and process-death evidence remain separate gates.
