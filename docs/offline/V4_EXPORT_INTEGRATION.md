# Native v4 export and Files integration

Both apps encode receipt-free authenticated metadata and one raw receipt at a time into the existing framed crypto writer. Individual JSON records are sorted by domain and ASCII ID, byte counts use the actual encoder, and END authenticates the checked logical transcript. No aggregate receipt base64 graph or plaintext archive file is created on this path. Current admission remains 10,000 expenses, 100 receipts, 2 MiB per receipt, 8 MiB aggregate receipts, 15,727,872 bytes of policy metadata and 20 MiB ciphertext. Exact legacy candidate/export capacity checks still apply.

iOS captures local authority before worker authentication and acquires existing shared receipt-directory locks while briefly holding the storage lease. The captured metadata and receipt pins then survive ordinary edits and garbage collection. Android holds its existing database transaction and lock during bounded worker emission because active rows can change in place. Ordinary Android writes wait during that export. Neither implementation establishes large-capacity or constant-memory live storage.

The writer owns a private encrypted output, checks actual sync/close, and runs the app reader with native image validation over the completed ciphertext. Checked identity, counts, digest, EOF and summary must agree before returning an opaque file capability. Subsequent exported streams verify the captured ciphertext digest and count. Files export copies from this internal capability and verifies the destination independently. Cloud publication remains a separate integration.

Files restore retains the existing preview and explicit replacement flow. A healthy-target v4 preview holds an opaque one-shot candidate and displays a separate receipt-free summary. Cancellation, stale results and dismissal relinquish candidate ownership; validation does not publish the candidate. Legacy v1–3 archives retain their bounded decoder and recovery path. iOS preserves any original target-capture failure until format dispatch so a failed current key cannot block legacy preview. A v4 archive never falls back to a legacy parser.

iOS copies the selected security-scoped URL inside one coordinated worker read to the same protected ciphertext snapshot used by both passes. Android opens one provider stream on IO, sniffs and replays the prefix, then acquires its private snapshot. Android's platform no_backup directory is commonly mode0771; a private0700 child is used for ciphertext without changing the platform directory. Actual controller testing exposed and corrected the prior directory assumption.

[Shared native writer fixtures](../../packages/offline-contract/fixtures/v4-native-writer-v1/README.md) retain actual native outputs and expected synthetic records. Opposite-platform tests require authentication, guarded installation, fresh-store reopen and exact record/receipt comparison. Captured files are not reproducibly encrypted with test randomness.

The runtime reports distinguish first writer suites from additional reciprocal and controller overlays. Controller/worker tests do not establish the full system Files picker journey, physical device recovery, provider-hang interruption, OS disk-full/power-loss behavior or real cloud completion. Android asynchronous abandoned-candidate cleanup is best effort and can quarantine files after a cleanup failure.

The Files export UI captures a fresh backup UUID and creation time once, without changing the source vault identity or records. iOS coordinates security-scoped folder access and exclusively creates a protected destination; it retains only its own inode after complete native readback. Android prepares before CreateDocument, refuses nonempty or unsupported destinations, syncs/closes the file and performs bounded native URI readback. Android never deletes a provider object on failure; an unverified partial file may remain. Success reports a verified file, not remote upload completion. Platform [iOS](../../apps/ios/evidence/v4-files-export.md) and [Android](../../apps/android/evidence/v4-files-export.md) reports retain the actual picker runs and source overlays.

## Explicit current-cap repair

[In-place repair](evidence/v4-repair-integration.json) permits a fully validated v4 backup to replace a receiving vault whose local key is missing or whose encrypted state is corrupt. The repair-only preview holds a bounded complete Snapshot and an opaque binding to the actual raw source, namespace and key observation. This is not a fallback to the legacy archive parser or permission to authenticate a broken vault as empty. Healthy candidate preparation is unchanged.

Preview never provisions a device key. Explicit Replace rechecks source and key state before using the established publication/recovery path. A newly appearing or inaccessible key is a conflict. An exclusively created owned key may be retained after a failed confirmed attempt for a fresh explicit retry, or safely removed; foreign keys are never cleanup targets. Original target material is retained until replacement is verified.

Android repair requires readable SQLite tables and serializes participating same-database key writers; it does not repair physically unreadable SQLite pages or provide atomic Keystore creation across arbitrary processes. iOS uses atomic create-only Keychain insertion. Injected failures and new-store reopen do not establish physical power-loss or real-provider recovery. Existing caps and cloud-v1 remain unchanged.
