# Penny Offline finance snapshot v3

Frozen 2026-09-13 for the bounded P4 slice. This extends expense/receipt snapshot v2 under the same encrypted envelope format 1, AAD and capacity limits. Native implementations must consume shared golden and invalid fixtures before adoption. This is a contract, not a claim that either UI or migration is complete.

Every object has exactly the listed required keys. Nullable fields are explicitly JSON `null`; absent fields are invalid. IDs are canonical lowercase UUIDs, unique within each domain. Currency is exactly CAD. Money is safe integer cents: positive amounts are 1..99,999,999,999; fields explicitly allowing zero are 0..99,999,999,999. Checked aggregate totals must not exceed 999,999,999,999,999. Strings are valid Unicode scalars; names/merchants are trimmed 1..200 code points, descriptions/notes/source are 0..4000, emoji 0..16. Timestamps are strict UTC milliseconds, with updatedAt >= createdAt. Dates are Gregorian civil dates 0001-01-01..9999-12-31 and never timezone-converted.

## Exact stored fields

Top-level fields: `schemaVersion:3`, `snapshotId`, `vaultId`, `createdAt`, `expenses`, `attachments`, `budgets`, `incomeSources`, `incomeEntries`, `savingsGoals`, `savingsEntries`, `recurringExpenses`. Existing expense/attachment limits remain. Additional limits: 1,200 budgets; 1,000 income sources; 10,000 income entries; 1,000 savings goals; 10,000 savings entries; 1,000 recurring expense templates. Snapshot UTF-8 and export capacity limits apply across every domain, independently of these counts.

| --- | --- |

IDs are unique per domain; references identify the named domain, so equal UUIDs in different domains cannot redirect associations. Deleting a referenced source, goal or template is invalid: deactivate it instead. Expense-template occurrence pairs are unique. Editing a template does not retroactively alter posted expenses; historical occurrence dates remain valid civil dates even if the schedule later changes. The posting action validates the current schedule before creating a new occurrence.

## Deterministic calculations and posting

Recurrence queries take explicit inclusive civil from/to dates, at most 366 days apart, returning at most 367 occurrences. Weekly and biweekly schedules advance 7/14 Gregorian days from startDate. Monthly schedules use dayOfMonth or the start day; yearly schedules use the start month and dayOfMonth or start day. Clamp to the month's final valid day independently for each occurrence: Jan 31 -> Feb 28/29 -> Mar 31. Feb 29 yearly -> Feb 28 in a non-leap year. Start/end bounds are inclusive. Disabled income recurrence retains its configured schedule but proposes only startDate once; inactive sources/templates propose nothing.

Occurrence identity is the exact string `<source-or-template-UUID>/<YYYY-MM-DD>`. It is stable across devices and queries, and is not a filesystem path. Native posting must insert the financial entry and its occurrence reference in one local transaction. Retrying an already posted identity returns the existing record and never duplicates money. Scheduled income amounts, templates and monthly savings targets do not contribute to actual cash totals. Income entries are the only received-income ledger.

Monthly report totals use expenseDate, receivedDate and savings-entry date, independent of UTC metadata timestamps. Category totals follow the canonical category order; amounts remain integer cents. Net received minus expenses is a separate figure from savings contributions, which are internal allocations rather than additional spending. Templates and future unposted dues are excluded.

For each category, budgets are processed in chronological month order. When the current budget has rollover enabled and the immediately preceding calendar month has a budget, carry `max(0, previous available - previous spent)`. Missing months break carry; overspending never creates rollover debt. Available is current limit + carry; remaining may be negative. Compare threshold exactly using integer arithmetic, not floating point. Zero available and zero spent is unused; positive spent at zero available is over budget. NotificationsEnabled is a stored local preference, not evidence notification permission or delivery exists.

Savings current = openingMinor + sum(actual positive contributions). Never add monthlyContributionMinor automatically. Remaining is max(0,target-current); progress basis points use integer floor(current*10000/target) capped at 10000. A manually retained status is not overwritten by progress calculations. Withdrawals are explicitly unimplemented; do not map legacy negative entries into positive contributions. Reconcile any imported current balance against complete contribution history to avoid counting it twice: opening = original current - imported historical contributions, only when nonnegative and source completeness is established. Cached legacy progress/onTrack/monthsToGoal discrepancies require a migration report and quarantine, not silent omission.

CSV export sorts expenses by civil date then UUID and emits UTF-8 RFC-style quoted cells with doubled quotes and CRLF rows. Header fields are `id,date,merchant,amount,currency,category,description,note`. Money is unsigned decimal CAD with exactly two digits after the period. To prevent spreadsheet formula execution, prefix a single quote to user text whose first non-whitespace character is =,+,-,@, or whose first character is tab/CR/LF; then quote the entire cell. Quoting alone does not neutralize formulas.

## Backward read and migration

Strictly validate v1/v2 before upcasting. Copy all snapshot IDs, timestamps, expenses and receipt bytes unchanged; add empty finance arrays and expense defaults description="", recurringTemplateId=null, recurringOccurrenceDate=null. Never downgrade v3. The prior v1->v2 helper remains available for P2 compatibility; the finance upgrade helper targets v3.

Legacy CAD amounts convert only through exact cent parsing, with explicit timezone decisions for timestamp-to-civil conversion. The new description/note split can preserve both original expense fields. Budget period, rollover and threshold preference; income gross/net/taxability/frequency/recurrence/active flags; and savings target/current/contribution/status/priority/timeline/description/emoji are representable. Retain identity mappings and original source provenance in a migration report. Unsupported currency, sub-cent money, negative savings entries, incomplete history, conflicting derived balances, unknown fields and other unrepresented records must be quarantined. No source cloud data is modified or removed by conversion.
